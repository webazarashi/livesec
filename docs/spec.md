## 2. 免責・利用規約の方針

### 方針
- サイト・SaaSの全出力は「あくまでも参考情報」として提供する
- 利用規約・免責もこの方向でそろえる

### 表示箇所
| 箇所 | 表示内容（文案） |
|---|---|
| 全ページのフッター | 本サイトの情報は公開情報をもとに作成した参考情報です。正確性・完全性・最新性を保証するものではありません。対応の判断は、各製品の公式アドバイザリをご確認のうえ、ご自身の責任で行ってください。 |
| 記事の冒頭または末尾 | 本記事は公開時点の情報にもとづく参考情報です。最新の状況は参照元をご確認ください。 |
| 個別の判定結果（ダッシュボード・Slack） | この判定はバージョン情報の照合にもとづく参考情報です。実際に影響を受けるかは、該当機能の使用状況によって異なります。 |
| Ask AI 欄の注意書き | 6-7 の文案 |

- Ask AI のプリセット質問には「断定できない点は断定しない」「バージョン上の該当と実際の使用有無を分けて書く」を含める（6-3）

### 利用規約に盛り込む方向性
- 提供情報は参考情報であり、正確性・完全性・特定目的への適合性を保証しない
- 情報の利用によって生じた損害について責任を負わない（または上限を設ける）
- Ask AI で外部AIに渡した内容と、外部AIの回答について、一次対応まとめは関与・保証しない
- 第三者データソース（OSV、NVD など）の情報を含み、各ソースのライセンスに従って出典を表示する
- 登録されたスタック情報・「私の環境」の取り扱い（目的外利用しない、保存・削除の方針）

※ 最終的な規約文面は専門家の確認を推奨

| ランタイム | Node.js、Python、Ruby、PHP、Go 本体 |
| 基盤 | OpenSSL、OpenSSH、curl、Docker Engine、Kubernetes |

### 3-4. 注目対象：LINE SDK・LIFF
各言語のパッケージとしてSBOM経由で検出し、メディアでは注目トピックとして扱う。

| 対象 | 識別子の例 |
|---|---|
| LIFF SDK | `pkg:npm/%40line/liff` |
| LINE Messaging API SDK（Node.js） | `pkg:npm/%40line/bot-sdk` |
| 同（Python） | `pkg:pypi/line-bot-sdk` |
| 同（Ruby） | `pkg:gem/line-bot-api` |
| 同（PHP） | `pkg:composer/linecorp/line-bot-sdk` |
| 同（Go） | `pkg:golang/github.com/line/line-bot-sdk-go`（メジャーバージョン付きパス） |

- **LIFFをCDNの `<script>` で読み込んでいる場合はSBOMに出ない**ため、`stack.yaml` の `cdn_scripts` に記載してもらう
- パッケージ名は実装時に各レジストリで再確認する

## 6. Ask AI（この記事をもとにAIに相談する）

### 6-1. 方針
- ユーザーは結局「自分のAI」を信用する。一次対応まとめは**良い質問と正確な事実データを渡す役**に徹する
- サービス側ではLLMを動かさない。プロンプトは**ブラウザ側で組み立て**、自社のサーバには送らない
- 対応プロンプト・回答文3種（問い合わせ回答／全顧客向けお知らせ／社内報告）は、この機能のプリセットとして提供する

### 6-2. 画面構成（AI Heartland の Ask AI 欄を踏襲）
1. 見出し：「Ask AI　この記事をもとにAIに相談する」
2. 説明文：記事の内容を前提に、自分の環境に合わせた答えをAIに出させる旨
3. プリセットボタン（6-3）
4. 質問のテキストエリア（プリセットを押すと質問文が入る。自由に編集可）
5. 送信ボタン：「ChatGPTで相談 →」「Claudeで相談 →」「Geminiで相談 →」
6. リンク：「プロンプトをコピー（他のAI用）」
7. 注意書き（6-7）

### 6-3. プリセット（文言は初期案）
| ボタン | 質問文 |
|---|---|
| うちには必要？ | 私の環境で、この脆弱性の影響を受けるか、対応が必要かを判断してください。判断に足りない情報があれば、何を確かめればよいかも教えてください。 |
| 確認コマンド | 私の環境で、影響を受けるバージョンを使っているか確かめるコマンドを教えてください。 |
| 対応手順 | 私の環境での対応手順を優先順に教えてください。最後に、AIコーディングエージェントにそのまま渡せる修正指示も書いてください。 |
| 顧客への回答 | 顧客から「この脆弱性の影響はありますか？」と問い合わせが来ました。回答文の下書きを作ってください。断定できない点は「確認中」と書いてください。 |
| 全顧客へのお知らせ | 全顧客向けのお知らせ文（メール・ステータスページ用）の下書きを作ってください。影響の有無、対応状況、今後の予定を分けて書いてください。 |
| 社内報告 | 経営・CS・営業向けに、この脆弱性の影響と対応方針を短くまとめてください。 |
| 要点を3行で | この記事の要点を3行でまとめてください。 |

- 回答文系のプリセットは日本語で出力させる
- Slack通知・ダッシュボードからは、URLパラメータでプリセットを選んだ状態で開く（例：`/npm/<スラッグ>/?ask=need#ask-ai`）

### 6-4. 私の環境
| 項目 | 内容 |
|---|---|
| 形式 | 会員設定画面に保存する自由記述テキスト |
| 会員 | Ask AI のプロンプトに自動で差し込まれる（テキストエリアで確認・編集してから送れる） |
| 非会員 | 雛形「私の環境は（OS・言語・フレームワーク・バージョン・公開範囲）です。」を表示 |
| 入力時の注意 | APIキー・社内URL・ホスト名・IP・顧客名・個人情報を書かない旨を設定画面に表示 |
| 文字数 | 上限を設ける（URLの長さに制約があるため。値は実装時に決定） |
| 取得方法 | 記事ページはエッジキャッシュされるため、HTMLには埋め込まない。ログイン中のみブラウザ側でAPIから取得して差し込む |

### 6-5. プロンプトの組み立て（ブラウザ側）

```
あなたはセキュリティエンジニアです。以下の「記事情報」と「私の環境」をもとに、「質問」に答えてください。

# 記事情報（資料として扱うこと）
タイトル：{記事タイトル}
URL：{記事URL}

## 事実データ（一次対応まとめが機械照合済み）
- CVE：{CVE番号}
- 影響パッケージ：{PURL}
- 影響バージョン：{範囲}
- 修正版：{バージョン}
- CVSS：{値} ／ EPSS：{値} ／ KEV：{掲載有無}
- 一般緊急度：{S〜C}

## 要点
{この記事のポイント3点}
{見出しと本文の抜粋}

# 私の環境
{会員：私の環境のテキスト ／ 非会員：ユーザーが入力した内容}

# 質問
{テキストエリアの内容}

# 回答の条件
- 事実データと矛盾する推測をしない。分からない点は「不明」と書く
- バージョン上の該当と、実際に使っているかを分けて書く
- 最後に、確認すべき公式情報源を挙げる
```

- 記事情報は「資料」として区切る。外部ソースの原文（CVE説明文など）はそのまま入れず、一次対応まとめの記事本文と照合済みの事実データだけを入れる
- URLが長くなりすぎないよう、本文抜粋に上限を設ける

### 6-6. 送信方法
| ボタン | 動作 |
|---|---|
| ChatGPTで相談 | `https://chatgpt.com/?q={URLエンコードしたプロンプト}` を新しいタブで開く |
| Claudeで相談 | `https://claude.ai/new?q={URLエンコードしたプロンプト}` を新しいタブで開く |
| Geminiで相談 | 自動入力に対応していないため、プロンプトをクリップボードにコピーしてから `https://gemini.google.com/app` を開く |
| プロンプトをコピー | 他のAI用にクリップボードへコピー |

- 各サービスのURL仕様は変わりうるため、実装時と定期的に動作確認する
- プロンプトがURLの長さの上限を超える場合は、コピー方式に自動で切り替える

### 6-7. 注意書き（文案）
> 記事の要点（見出し・事実データ・本文の抜粋）と質問、ログイン中は「私の環境」が、選んだAIにそのまま渡ります。相談内容は当サイトのサーバには送信しません。Geminiは自動入力に対応していないため、押すとプロンプトをコピーしてGeminiを開きます。APIキー・社内のURL・個人情報は入力しないでください。AIの回答は記事の内容にもとづく参考情報です。

## 7. 緊急度判定

### 7-1. ランク
| ランク | 意味 | 通知 |
|---|---|---|
| S | 今すぐ対応 | Slack即時 |
| A | 24時間以内 | Slack即時 |
| B | 次の定期保守 | 週次まとめ（月曜09:00） |
| C | 記録のみ | 週次まとめ（月曜09:00） |

### 7-2. シグナルの定義
| シグナル | 定義 |
|---|---|
| CVSS | NVDの基本値。v3.1を優先し、なければv4.0。どちらも未算出ならGHSAの深刻度で代用（Critical=9.0／High=7.0／Moderate=4.0／Low=1.0） |
| EPSS | FIRSTのEPSSスコア（0〜1） |
| KEV | CISA KEV に掲載されている |
| PoC | 参照URLに exploit タグが付いたもの、または Exploit-DB・Metasploit 等へのリンクがある |

### 7-3. 一般緊急度（上から順に判定し、最初に当てはまったランク）
| ランク | 条件（いずれか） |
|---|---|
| S | KEV掲載／PoCあり かつ CVSS 9.0以上／EPSS 0.5以上 かつ CVSS 7.0以上 |
| A | CVSS 9.0以上／CVSS 7.0以上 かつ（PoCあり または EPSS 0.1以上） |
| B | CVSS 7.0以上／CVSS 4.0以上 かつ（PoCあり または EPSS 0.1以上） |
| C | 上記以外 |

- メディアの緊急トップには一般緊急度S・Aを掲載する
- **Sは悪用の兆候（KEV・PoC・高EPSS）があるものだけ**。個別の調整でSに上がることはない
- 閾値は設定ファイルで変えられるようにし、運用しながら調整する

### 7-4. 個別緊急度（一般緊急度に上から順に適用。ランクはS〜Cの範囲に収める）
| 順 | 条件 | 調整 |
|---|---|---|
| 1 | 該当バージョンを使っていない | 通知しない |
| 1 | バージョンが `unknown`（MWウォッチリスト） | B固定で終了（「バージョン確認が必要」と表示） |
| 2 | `exposure: internal` | 1段階下げ |
| 2 | `exposure: offline` | 2段階下げ |
| 3 | `data_sensitivity: high` かつ `exposure: internet` | 1段階上げ（上限A） |
| 3 | `data_sensitivity: low` | 1段階下げ |
| 4 | SBOMで開発用依存と判別できる | 1段階下げ |
| 5 | `managed: true` | 上限B（提供元のパッチ適用状況の確認を促す） |
| 6 | KEV掲載 かつ `managed: false` | 下限A（下げすぎ防止） |

### 7-5. 判定例
| 例 | 一般緊急度 | プロジェクトの文脈 | 結果 |
|---|---|---|---|
| 1 | B（CVSS 7.5、悪用の兆候なし） | internet・high | 3で **A** → 即時通知 |
| 2 | S（KEV掲載） | internal | 2でA → 6で下限A → **A** → 即時通知 |
| 3 | S（KEV掲載）のPostgreSQL | `managed: true` | 5で上限 **B** → 月曜の週次まとめ（提供元の対応確認を促す） |
| 4 | A | offline | 2で2段階下げ → **C** → 月曜の週次まとめ |

### 7-6. やらないこと
- **到達可能性の判定はしない**（脆弱な機能を実際に使っているかは見ない。バージョン一致で判定）
- そのため通知文には「バージョン上は該当（使用有無は未確認）」と明記する

## 8. スタック登録（照合・通知用）

※ Ask AI に入れる「私の環境」（6-4）とは別物。こちらは照合と通知のために使う。

### 8-1. 方式
- 先方のAIエージェントに、一次対応まとめが配布するプロンプトを渡して作成してもらう
- **SBOM（CycloneDX JSON）は必須**。生成は cdxgen を想定
- 文脈情報は `stack.yaml`、パッケージの事実は `bom.json`
- 識別子はPURLで統一
- `stack.yaml` のバージョンは必ず文字列でクォートし、JSON Schemaで検証する

### 8-2. 更新タイミング
- CIでデプロイごとに自動送信（GitHub Actions 等のテンプレートを配布）
- 手動（エージェントに依頼して再生成・送信）も可
- 最終更新からの経過日数をダッシュボードと週次まとめに表示する

### 8-3. `stack.yaml` サンプル

```yaml
# 先方のAIエージェントが生成 → 人がレビュー → 一次対応まとめへ送信
schema_version: "1.0"
generated_at: "2026-10-29T17:00:00+09:00"
generated_by: "claude-code"
service:
  name: "acme-crm"
  data_sensitivity: "high"        # high / medium / low

components:
  - name: "api-server"
    exposure: "internet"          # internet / internal / offline
    exposure_reason: "ALB経由で公開（infra/alb.tf）"
    managed: false
    sbom: "sbom/api-server.cdx.json"
    image:
      purl: "pkg:docker/node@20.18.1-bookworm-slim"
      evidence: "Dockerfile"
    middleware:
      - purl: "pkg:generic/nginx@1.27.3"
        evidence: "docker-compose.yml"

  - name: "web-liff"
    exposure: "internet"
    exposure_reason: "LINEミニアプリとして公開"
    managed: false
    sbom: "sbom/web-liff.cdx.json"
    cdn_scripts:                  # SBOMに出ないCDN読み込み
      - name: "LIFF SDK"
        url: "https://static.line-scdn.net/liff/edge/2/sdk.js"
        evidence: "src/index.html"

  - name: "main-db"
    exposure: "internal"
    exposure_reason: "VPC内のみ"
    managed: true                 # RDS等。パッチは提供元
    middleware:
      - purl: "pkg:generic/postgresql@16.4"
        evidence: "infra/rds.tf"
```

### 8-4. 先方エージェントに渡すプロンプトの骨子
1. lockfile・Dockerfile・docker-compose・IaC・CI設定・HTML内の `<script>` を探索する
2. cdxgen でコンポーネントごとに SBOM（CycloneDX JSON）を生成する（コンテナイメージがあればOSパッケージも含める）
3. バージョンは必ず根拠ファイルから読み、`evidence` にファイル名を書く。読めなければ `"unknown"`
4. コンポーネントごとに `exposure` を判定し、理由を `exposure_reason` に残す
5. ホスト名・IP・URL（CDN以外）・環境変数の値・秘密情報は書かない
6. JSON Schemaで検証し、人のレビューを促してから送信する

## 9. 突合

### 9-1. 言語パッケージ・OSパッケージ
```
bom.json から PURL 一覧を抽出
→ 全テナントの「パッケージ＋バージョン」を重複排除
→ OSV querybatch（1回最大1000件）を3時間ごとに実行
→ 前回結果との差分 ＝ 新たに該当したCVE
→ 個別緊急度を計算 → 通知
```
- 実行周期：**3時間ごと**（CVEカタログの取り込みも同じ周期で行い、取り込み → 再照会の順に実行）
- プロジェクトの `stack.yaml` ＋ `bom.json` が新規登録・更新されたときは、そのプロジェクト分だけ即時に照会する
- querybatch はIDと更新日時のみ返すため、詳細は `/v1/vulns/{id}` で取得してD1にキャッシュ
- OSV停止時に備えて結果キャッシュとリトライを持つ

### 9-2. ミドルウェア・ランタイム
- ウォッチリスト（3-3）だけをNVDのCPEで突合（自前実装）
- `stack.yaml` の `middleware` を固定の別名表でCPEに対応づける
- バージョン比較は数字ドット区切りの比較器1つで対応

## 10. 記事

### 10-1. 生成方法
- **記事生成は ChatGPT のテキストチャット（サブスク）で行う**（サービス側で唯一AIを使う工程。APIは使わない）
- 対象範囲の直近1ヶ月分のCVEは**すべて記事化**する
- 件数が多いため、管理画面では**複数件をまとめてコピー・まとめて貼り付け**できるようにする（1件ごとの区切り形式を固定し、貼り付け時に分割して取り込む）
- 流れ：
  1. 管理画面に「記事待ちCVE一覧」を表示（対象範囲のみ、緊急度順）
  2. 「記事生成プロンプトをコピー」でCVEの事実データ（CVE番号、影響範囲、修正版、CVSS、EPSS、KEV、参照URL）＋記事テンプレート＋トーン指定を一括コピー
  3. ChatGPTに貼って生成し、出力（10-3の固定形式）を管理画面に貼り付け
  4. 機械照合ゲートを通過したら公開、不一致なら差し戻し表示
  5. ソース側が更新されたら「要更新」フラグを立てて再生成対象に戻す

### 10-2. 機械照合ゲート
- 記事中のCVE番号・影響バージョン・修正版・CVSSをソースデータと突き合わせる
- 1つでも不一致なら公開しない
- 記事ページの「事実データ」ブロック（5-3）は記事本文ではなくDBの値を表示する
- 訂正時は訂正履歴を残す

### 10-3. ChatGPTに出させる固定形式
```markdown
=====ARTICLE=====
---
cve_ids: ["CVE-2026-XXXXX"]
title: "製品名 CVE番号｜何が起きるか｜修正版"
slug: "express-cve-2026-xxxxx"
topic: "npm"
packages: ["pkg:npm/express"]
affected: ">=4.0.0 <4.21.2"
fixed: ["4.21.2"]
cvss: 7.5
why_read: "なぜ読むべきか（1〜2文）"
points: ["ポイント1", "ポイント2", "ポイント3"]
gains: ["この記事で得られること1", "2", "3"]
faq:
  - q: "質問"
    a: "回答"
sources:
  - title: "参照元タイトル"
    url: "https://..."
    note: "一言説明"
---
（本文：見出し・表・コードブロック・章末のまとめボックス・自環境の確認コマンド・まとめ）
```
- `=====ARTICLE=====` を1件ごとの区切りにして、まとめて貼り付けたものを分割する
- 機械照合は `cve_ids`・`affected`・`fixed`・`cvss` で行う

## 11. アーキテクチャ

| 領域 | 決定 |
|---|---|
| 基盤 | Cloudflare中心 |
| 言語 | TypeScript統一 |
| 体制 | 1人＋AIエージェント |
| メディア | Astro on Workers（SSR＋エッジキャッシュ、CVE更新時にパージ） |
| API | Hono |
| DB | D1を2つ：CVEカタログ用／アプリ用（アプリ側は単一D1＋tenant_id） |
| 原本保存 | R2（ソースJSONを全保存。記事の再生成・訂正の根拠） |
| パイプライン | Cron Triggers → Queues → Workflows |
| ランキング集計 | Workers Analytics Engine で集計 → 定期的にD1へ確定 |
| 認証 | Better Auth × D1（メールアドレス＋パスワード） |
| LLM | **サービス側では使わない**。記事はChatGPT（手動）、それ以外はAsk AI（ユーザーのAI） |
| 通知 | Slack Incoming Webhook |
| 公開URL | `workers.dev`（独自ドメインなし）。Better Auth の `baseURL`・信頼するオリジンもこのURLに合わせる |
| 定期実行 | 取り込み＋OSV再照会：3時間ごと（`0 */3 * * *`）／週次まとめ：月曜09:00 JST（`0 0 * * 1`。Cron TriggersはUTC指定のため、JST 09:00 = UTC 00:00） |
| スタック受付 | プロジェクトごとのAPIトークンでPOST（画面からのアップロードも可） |

### 全体図
```
[外部ソース] OSV / NVD / CISA KEV / EPSS
      │ Cron Triggers（3時間ごと）
      ▼
[Ingest] → 生JSONをR2へ → [Queues] → [Normalize] → D1（CVEカタログ）
      │
      ├─▶ [Scoring] 一般緊急度 S〜C
      ├─▶ [記事待ち一覧] → 管理画面 → ChatGPT（手動）→ 貼り付け → 機械照合 → 公開
      └─▶ [Matcher] OSV querybatch 差分 ＋ MWウォッチリスト → 個別緊急度
                         ├─▶ Slack（S・A即時 / B以下は月曜09:00）
                         └─▶ ダッシュボード（状態管理）

[メディア] Astro on Workers ← D1 / R2
           └─ 記事下部の Ask AI：ブラウザでプロンプトを組み立て
                → ChatGPT / Claude / Gemini（ユーザー自身のAI）
                  ※ 会員はログイン後に「私の環境」をAPIから取得して差し込む
[SaaS]   ダッシュボード ＋ API（Hono）＋ Better Auth
```

## 12. 実装時に初日から入れること

| 対象 | 内容 |
|---|---|
| テナント分離 | 全クエリを「tenant_id必須」のリポジトリ層経由に限定。他テナントを読めないことをテストで保証 |
| Webhook URL | 秘密情報として暗号化保存 |
| 認証 | MFA、ログイン試行のレート制限、セッション失効 |
| 私の環境 | キャッシュされるHTMLに埋め込まない。ログイン中のみAPIから取得 |
| Ask AI のプロンプト | 記事情報は「資料」として区切り、外部ソースの原文は入れない |
| D1の制約 | 1DBあたり10GB・単一スレッド → カタログとアプリを分離済み |
| 出典表示 | 各データソースのライセンスに従ったクレジット表示 |

## 13. MVPの範囲

### 含む
- メディア：5章の構成一式（トップ・記事・トピック・ランキング24時間／月間・緊急・保存・免責）
- 記事：直近1ヶ月分すべて（ChatGPT手動生成＋機械照合）、まとめてコピー・まとめて貼り付け
- Ask AI：全記事に設置、プリセット7種、ChatGPT／Claude／Gemini／コピー
- 会員登録・ログイン（Better Auth、メールアドレス＋パスワード）と「私の環境」
- プロジェクト登録（`stack.yaml` ＋ `bom.json`、API・画面）
- 突合（OSV＋MWウォッチリスト、3時間ごと）と緊急度判定（7章の基準）
- ダッシュボード（アラート一覧と状態管理）
- Slack通知（S・A即時、B以下は月曜09:00の週次まとめ）
- 管理画面（記事待ち一覧、記事の取り込み・公開、EDITOR'S PICKのピン留め）
- `workers.dev` での公開

### 含まない
- 課金（Stripe等）
- サービス側でのLLM処理（Claude API・Gemini API）
- 到達可能性の判定
- 英語の回答文
- 独自ドメイン

### データ
- **直近1ヶ月分のCVE**から開始（初回取り込み時点から30日遡る）
